# Viarde Project Tracker

Автоматический трекер состояния 3D-визуализационных проектов на основе структуры папок Dropbox.

---

## 1. Контекст и постановка задачи

### Кто мы

Viarde Studio — команда 3D-визуализации. Делаем рендеры кухонных моек и смесителей для американской компании **Kraus**. Вся работа живёт в Dropbox (тариф Advanced, 25 ТБ, ~10 участников, team space включён).

### Проблема

Пробовали Jira и Trello. Не прижилось: карточки надо двигать руками, никто этого не делает, доска врёт уже через неделю. При этом **реальное состояние проекта уже полностью закодировано в структуре папок** — просто никто это не читает автоматически.

### Идея

Веб-приложение с канбан-доской, где **карточки двигаются сами**. Приложение следит за Dropbox и выводит стадию проекта из того, какие папки появились. Руками — почти ничего.

### Ключевой принцип

> Файловая система — источник истины. Приложение её **читает**, а не редактирует.

Пользователь может вручную закрепить карточку (пин), но по умолчанию всё вычисляется.

### Критично: папка в 05_Outbox = отправлено клиенту

По регламенту студии, если папка собрана в Outbox — ссылка на неё уже у клиента. Это **надёжнее**, чем шаринг-ссылки через API (ссылка могла быть создана и не отправлена).

### Критично: пустая папка сцены = моделинг

Если в `04_JPG` есть папка с именем сцены, но в ней нет изображений — сцена ещё в моделинге. Есть изображения — визуализация.

Отсюда важное следствие: **список ожидаемых сцен известен заранее**, значит можно считать не бинарный статус, а прогресс (например «отрендерено 9 из 14 сцен»).

## 3. Модель стадий

| Вес | Стадия | Сигнал |
|-----|--------|--------|
| 0 | Новый проект | есть `01_Clients/Directions - *`, нет моделей |
| 1 | Моделинг | есть `03_Models` ИЛИ все сцены в `04_JPG` пустые |
| 2 | Fast Preview у клиента | `05_Outbox/*Fast_Preview*` |
| 3 | Визуализация | в папках сцен `04_JPG` появились изображения |
| 4 | Preview у клиента | `05_Outbox/*Preview*` (без Fast, без Pre) |
| 5 | Prefinal у клиента | `05_Outbox/*Prefinal*` |
| 6 | Финал | `05_Outbox/*Final*` |

### Правила вычисления

1. **Стадия = максимум** между «стадией из сцен» и «стадией из Outbox».
2. **Монотонность вперёд.** Статус не откатывается назад. Появление `04_JPG/.../002` после отправленного Preview — это не откат в «Визуализацию», а **круг правок №2**.
3. **Дебаунс.** Рендер пишет файлы часами. Переход подтверждается только если в папку N минут (по умолчанию 15) ничего не добавлялось. До этого — «в работе».
4. **Круг правок** = максимальный номер среди папок Outbox текущей стадии.
5. **Ручной пин** замораживает карточку до появления сигнала с бо́льшим весом.

### Порядок проверки суффиксов Outbox (ВАЖЕН!)

```
prefinal → fast_preview → final → preview
```

Если проверять `final` до `prefinal`, то `Prefinal` ошибочно распознается как `Final`. Аналогично `preview` поймает `Fast_Preview`.

## 5. Что НЕ выводится из папок

| Данные | Решение |
|--------|---------|
| Клиент посмотрел превью, но ещё не ответил | ревью-портал (Фаза 4) — единственное настоящее белое пятно |
| Тексты комментариев клиента | ревью-портал; частично ловится по папкам `comments_*`, `*_Post_references` в `01_Clients` |
| Дедлайн, приоритет, ответственный | манифест `project.json` в корне проекта, приложение его читает **и пишет** |
| Пауза / отмена | конвенция: префикс `_onhold` к имени папки, либо клик в UI |

**Манифест `project.json`** кладётся в корень проекта. Метаданные живут вместе с проектом, переживают миграцию приложения и видны без него.

```json
{
  "deadline": "2026-09-15",
  "priority": "high",
  "assignees": ["a.demchenko", "v.chaban"],
  "status": "active",
  "notes": "Клиент просил акцент на отличии SFACB от SFBB"
}
```

## 6. Whitelist файлов

Мусор в папках (`.DS_Store`, `Thumbs.db`, `desktop.ini`, временные файлы 3ds Max) не должен переводить сцену в «визуализацию».

**Подход: whitelist по паттерну имени + расширение + минимальный размер.**

- Расширения: `.jpg`, `.jpeg`, `.png`, `.tif`, `.tiff`, `.exr`, `.webp`
- Минимальный размер: 100 КБ (финальный рендер весит мегабайты, превью из вьюпорта — килобайты)
- Имя матчится на паттерн артикула

### Обратная сторона whitelist

У whitelist есть **ложноотрицательные срабатывания**: сцена отрендерена, но файлы названы не по конвенции → карточка молча висит в «моделинге». Это хуже ложного перехода, потому что незаметно.

**Решение:** если в папке есть файлы с рендерными расширениями, но ни один не прошёл паттерн — папка **не** переводится в визуализацию, но помечается флагом «нераспознанные файлы» с бейджем на карточке и кнопкой «принять как валидные». Один клик — правило расширяется. Система сама подсвечивает отклонения вместо того, чтобы тихо врать.

## 7. Архитектура

### Стек

- **Frontend:** Next.js 15 (App Router), TypeScript, SCSS-модули, TanStack Query
- **БД:** PostgreSQL + Drizzle ORM
- **Очередь:** BullMQ + Redis
- **Хостинг:** VPS, docker compose (Postgres + Redis + Next.js + воркер)
- **Хранилище превью:** S3-совместимое (Cloudflare R2)
- **Авторизация:** Google OAuth + роли

**Почему VPS, а не Vercel:** первичный обход метаданных 23 ТБ займёт часы непрерывной работы. В serverless это упрётся в таймауты и потребует костылей. На VPS просто крутится воркер. ~10 €/мес.

### Интеграция с Dropbox

**Тип приложения:** team app (не user app). Скоупы уровня команды:
- `files.metadata.read` — метаданные файлов и папок
- `files.content.read` — миниатюры
- `team_data.member` — доступ к пространству команды
- `events.read` — журнал событий команды (доступен на Advanced)
- `members.read` — атрибуция действий

**Критично — team space namespace.** На Advanced включено командное пространство. Обычный токен покажет только личную папку админа, и проекты не найдутся. Нужен заголовок `Dropbox-API-Path-Root` с root namespace из `users/get_current_account`. Это самая частая засада, заложить время на отладку.

**Критично — идентификация по file_id, а не по пути.** Dropbox выдаёт стабильный `id:...` для папки, который переживает переименование и перемещение. Если привязываться к пути, первый же переименованный проект породит дубль карточки.

**Синхронизация:**

1. **Первичный обход:** `files/list_folder` рекурсивно, сохранение курсора после каждой страницы (возобновляемость при падении)
2. **Дельта:** `files/list_folder/continue` по курсору
3. **Webhook:** Dropbox дёргает endpoint при изменениях. Он **не присылает сами изменения**, только «у аккаунта что-то поменялось». Надо за 10 секунд ответить 200 и поставить задачу в очередь, воркер идёт за дельтой.
   - Верификация: GET-challenge при подключении, HMAC-подпись на POST
4. **Страховка:** longpoll + cron полной пересинхронизации раз в час (webhook иногда теряется)

**Файлы не скачиваем никогда** — только метаданные и миниатюры. 23 ТБ не пугают, они лишь растягивают первый запуск.

**Превью:** Dropbox отдаёт готовые thumbnails для jpg/png. Кешировать в R2. Для PSD/EXR превью нет — брать jpg-двойник из `04_JPG`. Тянуть **лениво**, только для видимого на экране.

### Журнал событий команды (бонус Advanced)

Даёт две вещи:
- **Атрибуция:** не «проект переехал в Prefinal», а «Василий собрал Outbox в 18:40»
- **Обратный засев истории:** журнал хранит прошлые события → можно восстановить, когда старые проекты проходили этапы, и построить статистику по времени цикла **сразу**, не дожидаясь полугода накопления

## 9. UI: чем доска отличается от Jira

Jira скучна, потому что там текст. У нас — картинки.

- **Карточка = превью последнего рендера**, а не заголовок тикета. Сетка миниатюр.
- На карточке: номер джоба, название, прогресс по сценам (9/14), круг правок, **сколько дней в стадии** (жёлтый/красный при застое)
- **Разворот карточки:** все сцены, версии `001/002/003` рядом, слайдер сравнения «до/после». Для истории с оттенками золота (SFACB vs SFBB) — прямо в тему.
- **Фильтры по SKU и типу финиша** — за секунду найти все сцены, где рендерили SFACB
- **Бейдж «нераспознанные файлы»** с кнопкой быстрого исправления правила

### Аналитика

То, чего никогда не получить из ручной Jira, потому что никто не двигает карточки честно. Здесь данные объективны — из файловой системы.

- Среднее время моделинга, среднее время до финала
- Сколько кругов правок на проект (найден рекорд — 8)
- Кто узкое горлышко (из journal событий)
- Отчёты по SKU и финишам

### Уведомления

Telegram/Slack: «Kraus_211 переехал в Prefinal», дневной дайджест «застряло больше 5 дней».

## 10. Отдельно: мониторинг места (горит)

**23,1 из 25 ТБ занято (92%).** Из них 22,5 ТБ — общие файлы, 600 ГБ — личные. Когда место кончится, Dropbox остановит синхронизацию у всех, и работа встанет посреди сдачи проекта.

Приложение и так обходит все папки, значит бесплатно знает вес каждого проекта:

- Виджет заполненности + алерт в Telegram при 95%
- Топ проектов по объёму, разбивка EXR / PSD / JPG
- **Список кандидатов на архив:** проекты в статусе Final старше полугода, к которым не обращались. Выгрузили на холодное хранилище (Backblaze B2 / Wasabi — в разы дешевле за терабайт), освободили место. Карточка остаётся в трекере с превью и метаданными, помечена «в архиве».

Параллельно — запрос в поддержку Dropbox на расширение квоты (на Advanced расширяется).

## 11. План по фазам

### Фаза 0 — Аудит конвенций ✅ в работе

Скрипт `analyze.ts` (готов): сканирует диск локально, парсит проекты и сцены, определяет стадию, выводит таблицу и список отклонений.

**Цель:** убедиться, что распознавание совпадает с реальностью, до написания приложения.

**Выход:** отчёт `report.json` + `anomalies.txt` + письменный документ с конвенцией именования + разовая чистка папок.

Это самая недооценённая и самая важная фаза. Без неё всё остальное утонет в исключениях.

### Фаза 1 — Синхронизация и парсинг (1–1.5 недели)

OAuth team app, root namespace, полный обход, курсоры, БД, парсер имён. UI — простая таблица, без доски.

### Фаза 1.5 — Отчёт по объёмам (2 дня)

Вставляется сразу после Фазы 1, пока горит место. Синхронизация уже готова, отчёт по весу — пара дней. Хороший способ показать команде пользу до появления доски.

### Фаза 2 — Движок правил и доска (1.5–2 недели)

Правила в БД, вычисление стадии, дебаунс, монотонность, круги правок. Канбан с превью, ручной пин, аудит переходов.

### Фаза 3 — Реалтайм и оповещения (1 неделя)

Webhook, очередь, longpoll и cron как страховка, Telegram, дайджест, детект застоя.

### Фаза 4 — Ревью-портал для клиента (2–3 недели)

Публичная страница по токену. Клиент видит рендеры, ставит булавки прямо на изображении, пишет комментарии. Первый комментарий → карточка автоматом в «Получены комментарии».

**Это главная ценность продукта:** закрывает единственное настоящее белое пятно и убивает почту как канал правок.

### Фаза 5 — Аналитика (1 неделя)

Время в стадиях, циклы, нагрузка по людям, отчёты по SKU.

**Итого до полезного состояния (Фазы 0–3): месяц-полтора неполной занятости.**

## 12. Что есть на рынке (для справки)

**CG-пайплайн:** Kitsu (open source, Python/Vue — стоит подсмотреть модель данных и UI ревью), ftrack, Autodesk Flow / ShotGrid, Cerebro, Aquarium. Все про «задачи», а не про «следим за папками». Тяжёлые, заточены под кино.

**Ревью:** Frame.io, Dropbox Replay, Filestage, Pastel — аннотации на изображении.

**Low-code:** Make.com / Zapier — триггер «новая папка» → карточка в Trello. Правила примитивные, состояние не пересчитывается, дебаунса нет.

**Готового «read-only трекера, который выводит статус из структуры папок» — нет.**

## 14. Подводные камни (чеклист)

1. **Team space namespace** — без заголовка `Dropbox-API-Path-Root` приложение не увидит проекты
2. **file_id вместо путей** — иначе дубли при переименовании
3. **Порядок проверки суффиксов** — prefinal до final, fast_preview до preview
4. **Дебаунс перед переходом** — иначе карточка уедет в «отправлено» в момент создания пустой папки
5. **Служебные папки** (`Studio`, `OLD`) — без фильтра проект застрянет в моделинге навсегда
6. **Smart Sync плейсхолдеры** — `stat` на онлайн-файлах может вернуть нулевой размер, фильтр по размеру их отсечёт
7. **Webhook отвечает за 10 секунд** — вся работа в очередь, не в обработчик
8. **Первичный обход возобновляемый** — сохранять курсор после каждой страницы
9. **Rate limits Dropbox** — при обходе сотен тысяч файлов нужен backoff
10. **Ложноотрицательные whitelist** — флаг «нераспознано» вместо тихого пропуска
