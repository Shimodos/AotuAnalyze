# План: состояние проектов из Dropbox API вместо обхода диска

Ноябрь 2026. Черновик к обсуждению — ничего из этого ещё не сделано.

## Зачем

Сейчас трекер узнаёт состояние проектов обходом локальной папки Dropbox. Папка
лежит на внешнем USB-диске, работает через Windows Cloud Files, и в ней
~430 тыс. файлов. Отсюда три проблемы, которые сменой языка не лечатся:

- обход диска конкурирует с самим Dropbox за один медленный диск (сканы до 38 минут);
- чтение содержимого онлайн-файла заставляет Dropbox его скачивать;
- программа привязана к машине, где папка синхронизирована.

Dropbox API отдаёт те же сведения (имена, размеры, даты файлов) без единого
обращения к диску. Тогда трекеру всё равно, где лежит папка, скачаны ли файлы
и на какой ОС он запущен.

## Что не меняется

Правила стадий (`scanner/stage.ts`), разбор имён (`scanner/parse.ts`), привязка
плана (`assignPlans`), запись в базу и история (`sync/sync.ts`), весь интерфейс.
Граница уже есть: `sync.ts` получает `ScannedProject[]` и не знает, откуда они.
Новый источник обязан вернуть ту же структуру.

## Что подтверждено документацией Dropbox

- `files/list_folder` с `recursive: true` отдаёт содержимое подпапок; дальше
  `files/list_folder/continue` по курсору, пока `has_more` не станет false.
  Позже тот же курсор возвращает только изменения.
- Просроченный курсор даёт ошибку 409 `reset` — нужно перечитать заново.
- `files/list_folder/longpoll` висит, пока что-то не изменится, и сообщает
  только сам факт; что именно изменилось — узнаём через `continue`.
- Для настольных приложений Dropbox рекомендует вход по PKCE с refresh-токеном;
  секрет приложения при этом не нужен ни при входе, ни при обновлении токена.
- Превью: `files/get_thumbnail_v2` и `files/get_thumbnail_batch`, официально для
  изображений до 20 МБ (jpg, png, tiff, gif, bmp). Лимиты запросов не
  опубликованы; при превышении приходит 429 с заголовком `Retry-After`.

Командное пространство (`Dropbox-API-Path-Root`) в проекте уже работает —
`src/dropbox/client.ts`.

Единственное расхождение — `Kraus_147_Bolden_Beverage_Faucet`: на этой машине
синхронизированы только 4 из 8 папок проекта (нет `04_JPG`, `04_EXR`, `04_PSD`,
`02_Inspiration`), а API видит все. Диск считает, что сцен нет; индекс находит
3 сцены и 38 PSD. Здесь прав индекс.

Что вскрылось по дороге:

- **Одинаковые даты решались порядком перебора.** У `Kraus_205` папки `Final`
  и `Prefinal` имеют одну и ту же дату последнего файла (файл скопирован из
  одной в другую). `stage.ts` берёт первую встреченную, на диске это `Final`
  только потому, что она раньше по алфавиту. Индекс отдавал записи в другом
  порядке и ставил проект в Prefinal. Исправлено порядком как у NTFS в
  `remote/fs.ts`; само правило в `stage.ts` не менялось и остаётся хрупким.
- **Обложка при кадрах одной секунды.** Dropbox хранит дату файла до секунды,
  диск точнее. Если два кадра сохранены в одну секунду, обложкой может стать
  другой из них (2 случая). На стадию не влияет.

**Доска переключена на индекс (18.11.2026).** Процесс скана (`scripts/scan.ts`)
по умолчанию обновляет индекс и считает стадии по нему; `VIARDE_SOURCE=disk`
или флаг `--disk` возвращают обход диска. Проверено на работающем трекере:
скан 23 проектов занял 1,0 с вместе с обновлением индекса, колонки не

## Результаты этапа 4 (18.11.2026)

Наблюдатель `src/remote/watch.ts` запускается вместе с сервером (и в dev, и в
сборке): ждёт сигнала от Dropbox через `files/list_folder/longpoll`, применяет

Доска в этом режиме опрашивает сервер каждые 20 с вместо 5 минут.

| Что | Результат |
|---|---|
| `longpoll` без заголовка авторизации | работает; при таймауте 30 с ответ пришёл через 46 с — Dropbox добавляет свою задержку |
| Запуск вместе с сервером | в логе «наблюдатель Dropbox запущен», у процесса одно ожидающее соединение с `notify.dropboxapi.com` |
| Скан при старте | запустился сам по устареванию данных |
| Реакция на настоящее изменение | **не проверена**: за несколько минут наблюдения в Dropbox ничего не изменилось. Проверить: изменить файл в отслеживаемом проекте — в логе сервера должна появиться строка «Dropbox: изменений N, в отслеживаемых проектах M», а доска обновиться в пределах минуты |

Как устроено:

- таймаут ожидания 300 с; после сигнала пауза 10 с, чтобы пачка файлов пришла целиком;
- дельту применяет сам сервер (только сеть и короткие записи в базу), скан — отдельный процесс, как раньше;
- если скан уже идёт, наблюдатель дожидается и запускает ещё один, чтобы изменение не потерялось;
- после сбоя сети пауза 60 с и повтор; при отключённом Dropbox наблюдатель ждёт подключения;
- проверка «данные старше 30 минут» осталась страховкой и выполняется после каждого ожидания.

## Отдельно, после: «каждый запускает у себя»

Не входит в оценку выше и требует отдельного решения.

- Вход по PKCE — секрет приложения исчезает, пользователь нажимает
  «Подключить Dropbox» и ничего не вводит руками.
- Токен в хранилище ОС (Windows Credential Manager, macOS Keychain) вместо
  открытого текста в SQLite.
- Экран настроек: путь к папке, шаблон имён проектов (сейчас `Kraus_` и
  `D:/Viarde Studio Dropbox` зашиты в `src/config.ts` и `scanner/scan.ts`).
- Упаковка под Windows и Mac.

Открытый вопрос: при локальном запуске у каждого своя база. История переходов,
пины и чеклисты общими не будут. Если они должны быть общими — нужен либо
общий файл в самом Dropbox, либо всё-таки один сервер.

## Риски

- Первичная загрузка идёт по проектам и должна переживать обрыв: что уже
  прочитано, заново не читаем.
- Курсор корня будет приносить изменения по всем 640 тыс. записей, включая
  проекты, которые мы не отслеживаем; их нужно отбрасывать по пути. Сколько
  такого шума в сутки — не замерялось.
- `get_latest_cursor` для корня описан в документации, но пробой не проверялся.
- Без сети трекер показывает последнее известное состояние и не обновляется.
- Превью для файлов больше 20 МБ официально не гарантированы.
- Курсор не сообщает об изменениях доступа и прочих метаданных — нам они не нужны.
