# Ревью Viarde Tracker — сентябрь 2026

Повод: Dropbox на машине студии периодически переставал синхронизировать,
«падал» и потом долго догонял. Вопрос был — виновата ли программа. Ответ: нет,
но она замыкала петлю. Ниже — что нашли, что изменили и что осталось сделать
руками на машине.

Всё, что здесь утверждается, проверено по журналам Windows, замерами на реальном
дереве Dropbox и чтением исходников. Где что-то не проверялось — сказано прямо.

## 1. Среда

| Факт | Откуда |
|---|---|
| Dropbox лежит на **внешнем USB-диске** LaCie P9233, 3.7 ТБ, свободно 7.5 % | `Get-PhysicalDisk`: BusType USB, Disk 3 = D: |
| 429 776 файлов, 21 897 папок; из них 325 249 — онлайн-заглушки | обход `D:\Viarde Studio Dropbox` |
| Dropbox рекомендует не более 300 000 файлов на компьютер | help.dropbox.com/plans/large-deployments |
| USB selective suspend **включён** | `powercfg /query` → index 1 |
| 13 × `disk/153` «IO operation retried» на Disk 3 (10.09) | журнал System |
| `Ntfs/140` «failed to flush transaction log, corruption may occur, VolumeId D:» (26.08) | журнал System |
| 277 × `LiveKernelEvent 0x1a8` WATCHDOG за 16–19.09 | журнал Application |
| Во время переиндексации Dropbox: 110 мс на чтение, очередь диска 7.4 | `Get-Counter PhysicalDisk(3 D:)` |

Программа в дни сбоев ядра (16–19.09) **не работала** — база не менялась с 10.09.
Первопричина внешняя.

## 2. Как программа усиливала проблему

Скан диска в норме занимает 1.5 с. Тот же скан во время переиндексации Dropbox
занял **12 минут 6 секунд** (запись `scan_runs` 1083), а 10.09 — 38 минут.
Старый код:

- запускал скан **внутри процесса Next** синхронно → пока скан идёт, сервер не
  отвечает вообще;
- планировал следующий скан через 10 минут после окончания, независимо от того,
  сколько длился предыдущий → диску не давали восстановиться;
- опрашивал `/api/board` каждую минуту и при каждом фокусе окна;
- писал `_Revisions.txt` в Dropbox при каждой галочке и каждой паузе 700 мс при
  наборе заметки, с меткой времени в теле — каждая запись была новой ревизией.

## 3. Что нашли в коде

### Безопасность

Контекст: приложение доступно по сети студии (`npm start`), логина нет.

| | Где | Суть | Сделано |
|---|---|---|---|
| H1 | `/api/open` | `existsSync` без `isDirectory` — `explorer.exe <файл>` **запускает файл**. Dropbox общий: подрядчик кладёт `.exe`, шлёт POST — файл выполняется на сервере | `statSync().isDirectory()`, иначе 400 |
| H2 | `/api/open` | «localhost» проверяется по заголовку `Host` — подделывается из сети | оставлено как фильтр для браузера; документирован `next start -H 127.0.0.1`; вместе с H1 остаточный риск — «открыть окно проводника» |
| H3 | все POST | CSRF: `request.json()` не требует `Content-Type`, `fetch(..., {mode:'no-cors'})` с любого сайта проходит | `requireSameOrigin` (`Sec-Fetch-Site` / `Origin`) на всех мутирующих роутах |
| M1 | `/api/checklist` | `?scene=..\..\..` попадает в `path.join` → листинг любой папки диска D: | `isSafeSegment` для `scene` и `fileName`; `round` — целое ≥ 1; заметка ≤ 2000 символов |
| M2 | `/api/scan?sizes=1` | рекурсивный обход всего Dropbox в процессе сервера, без ограничений | скан — отдельным процессом |
| L2 | `/api/pin` | `request.json()` без try/catch → необработанный 500 | `readJson` → 400 |

Проверено и в порядке: OAuth `state` (16 случайных байт, httpOnly, SameSite=Lax),
`redirect_uri` только из env, секреты не в git и не в истории, SQL везде
параметризован, `/api/thumb` берёт путь из БД и проверяет корень.

### Потеря данных — `SceneChecklist.tsx`

| | Было | Стало |
|---|---|---|
| Заметка, набранная в последние 700 мс перед закрытием, терялась (таймер отменялся) | cleanup: `clearTimeout` | cleanup: отправка; плюс `onBlur` |
| Таймер замыкал `isDone` на момент набора; галочка, поставленная позже, снималась обратно | `save.mutate({ isDone: item.isDone })` из замыкания | `isDone` берётся из актуальных данных в момент отправки; `toggle()` отменяет таймер по этому кадру |
| Черновики без привязки к кругу: заметка круга 3 показывалась в круге 2 | `drafts[fileName]` навсегда | сброс черновиков при смене круга |
| Клик по фону чеклиста закрывал и панель проекта | событие всплывало | `stopPropagation` |

### Производительность (замеры на 30 проектах, 152 сценах, 163 отгрузках)

Профиль одного скана до правок: **13 135 `statSync`**, 1 910 `readdirSync`.
SQLite — суб-миллисекунды, не фактор.

| Что | Доля | Сделано |
|---|---|---|
| `05_Outbox`: stat каждого файла каждой отгрузки ради `max(mtime)` | 9 127 stat, 70 % | кеш сводок в `file_cache` по отпечатку дерева (mtime каталогов + имена) |
| xlsx-планы парсились заново в каждом процессе скана | 18 файлов, до 2.9 с на холодном диске | кеш разобранных групп в `file_cache` по mtime+size |
| Один каталог читался дважды (сцены, `01_Clients`) | 180 повторов | `scanImages` отдаёт подпапки; `01_Clients` читается один раз |
| Версии 001/002: stat каждого файла ради счётчика в подсказке | 1 292 stat, 10 % | счёт по расширению без stat |
| `/api/thumb`: синхронный `statSync` на USB на каждый запрос, 30 обложек | 30 блокировок сервера при загрузке доски | `cover_at` пишется при скане; хеш из БД; диск не трогается при попадании в кеш |
| Insert по одной строке, select проектов по одному | 175 мс | пакетные insert, один select → 63 мс |

**Результат: скан 3 024 мс → 506 мс на тёплом кеше.**

Компромисс, принятый осознанно: отпечаток дерева отгрузки не ловит перезапись
файла на месте под тем же именем (NTFS не меняет mtime каталога). Dropbox и
Photoshop пишут через временный файл и переименование, так что на практике
событие `deliveryReplaced` появится со следующим изменением в папке.

### Переусложнение и мусор

Архитектурно код не переусложнён. Убрано и сведено:

- **три механизма скана → один** (`sync/launch.ts`): доска, кнопка и prod-таймер
  зовут одну функцию; таймер больше не сканирует в процессе сервера и не
  запустит второй обход параллельно с дочерним;
- `tsx` переехал из `devDependencies` в `dependencies` — иначе после
  `npm ci --omit=dev` фоновый скан молча не стартовал бы;
- проверка «путь внутри корня» — была скопирована 5 раз с разночтениями, теперь
  одна (`server/paths.ts`); сборка пути к сцене/отгрузке — была 6 раз;
- `currentRound` — одна функция вместо формулы в двух файлах; блок сборки чеклиста
  общий для GET и POST;
- `fetchJson` вместо пяти копий `fetch → json → throw`; единая форма ошибок API;
- мёртвое: `listFileComments`, `CONFIG.boardFolders`, `isScanInProgress`,
  `scenes.max_version`, типы `ProjectRow`/`StageEventRow`, 10 ключей i18n;
- колонки-перечисления типизированы в схеме (`text(..., { enum })`) — ушли все
  касты `as Column`, `ball` больше не `string`;
- типы ответов API экспортируются из роутов, клиент их импортирует;
- 5 захардкоженных русских строк заменены существующими ключами словаря; CLI и
  `_Revisions.txt` приведены к одному языку с интерфейсом;
- `README` синхронизирован с кодом (дефолты переменных расходились).

## 5. Что осталось сделать руками — на машине, не в коде

Это даёт больше, чем всё вышеперечисленное вместе взятое.

1. **Выключить USB selective suspend.** Электропитание → схема «AMD Ryzen High
   Performance» → Дополнительные параметры → Параметры USB → Запрещено.
2. **`chkdsk D: /scan`** — после `Ntfs/140` обязательно.
3. **Кабель и порт.** LaCie в задний USB 3.0 на материнской плате, без хаба;
   новый кабель — `disk/153` чаще всего именно он.
4. **Selective Sync** — увести архивные проекты, уйти ниже 300 тыс. файлов.
5. Освободить место на D: — 7.5 % мало для тома, куда постоянно пишут.
6. Стратегически — перенести Dropbox на внутренний диск. Dropbox предупреждает:
   если внешний диск отключится при работающем клиенте, он может начать удалять
   файлы, не поняв, что пропал весь том.
7. Отозвать и перевыпустить `VIARDE_DROPBOX_TOKEN` в `.env.local` — он попал в
   вывод терминала во время диагностики.

## 6. Что не делалось и почему

- Полный try/catch вокруг транзакции в `runSync`: если упадёт запись в базу
  (не обход), запись `scan_runs` останется «идущей» до таймаута 2 ч. Случай
  маловероятный, дифф большой; при желании — отдельной правкой.
- PKCE для OAuth: для confidential-клиента с секретом на сервере допустимо по
  RFC 6749; усиление, не уязвимость.
- Токены Dropbox в SQLite открытым текстом: осознанный компромисс внутреннего
  инструмента, файл в `.gitignore`.
- Ограничение размера `.cache/thumbs`: растёт на ~13 КБ на замену обложки,
  годами не проблема.
